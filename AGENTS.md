# Ardoise Development Contract

## Reviewable and reversible edits

- Use the `apply_patch` tool for all manual text-file additions, edits, and deletions. Do not use Python, Perl, sed, shell redirection, or other scripts to rewrite project files.
- Project generators and formatters may update files when required by the task. Identify these tool-generated changes and review their diffs.
- Inspect Git status before editing, preserve pre-existing user changes, and keep edits uncommitted unless the user requests a commit. Review the final diff, run `git diff --check`, and report changed files, including new untracked files.
- Keep changes small so they can be reviewed and undone independently. When asked to undo work, revert only the agent's changes while preserving subsequent user edits; never use a broad reset or discard unrelated changes.

## Project identity

- **Repository:** `ardoise`
- **CMake package:** `Ardoise`
- **Public target:** `Ardoise::Widgets`
- **Public C++ namespace:** `Ardoise`
- **Technology:** C++20, Qt 6 Widgets, and CMake.
- **Target platforms:** Linux, macOS, and Windows.
- **Purpose:** provide a shared visual theme and reusable desktop widgets for Qt Widgets applications.
- **License:** MIT.

## Current scope

The 0.1 static library contains the dark Ardoise visual system, theme tokens,
a Fusion-based QProxyStyle, SVG icons, reusable controls, native window/dialog shells,
English/French chrome translations, a gallery and package/interaction tests.
See [docs/design-system.md](docs/design-system.md) for the durable visual contract.

The library is independent of the applications that use it. Applications depend
on Ardoise; Ardoise must never depend on an application.

## Repository layout

- `include/Ardoise/`: public headers, included as `<Ardoise/Header.h>`.
- `src/`: private implementation and the library target definition.
- `src/theme/`: theme tokens, palette, typography and shared style.
- `src/widgets/`: generic controls and private window behavior.
- `resources/`: bundled monochrome SVG assets.
- `cmake/`: package configuration and generated version-header templates.
- `examples/consumer/`: minimal example for source and installed-package integration.
- `examples/gallery/`: small interactive control gallery.
- `translations/`: English/French framework chrome catalogs.
- `tests/`: Qt interaction/rendering tests and CMake source/installed consumers.
- `docs/architecture.md`: current dependency boundaries and extension rules.
- `docs/screenshots/`: README images, generated by `scripts/screenshots.sh` from the gallery.
- `docs/release-notes/`: notes for each released version.
- `.github/`: CI and release workflows, issue templates and Dependabot.

## Development rules

- Implement small vertical slices and keep changes minimal.
- Use straightforward C++ and existing Qt facilities.
- Use Qt Widgets. Do not introduce QML, another UI toolkit, or a Python runtime.
- Keep dependencies minimal; runtime dependencies are Qt Widgets and SVG; LinguistTools is required to build.
- Keep all documentation, code comments, and user-facing source strings in English. The
  only exception is `README.fr.md`, the French translation of `README.md`; keep both in sync.
- Keep public headers self-contained and keep private implementation out of the public API.
- Add source files explicitly to CMake targets; do not use source globbing.
- Scope compiler features, warnings, include directories, and Qt code generation to targets.
- Do not change global build settings. Change application style/palette only through explicit Theme::apply().
- Build and run relevant tests after every implementation slice.
- Fix warnings and errors introduced by changes.
- Update README, CONTRIBUTING, and architecture documentation when requirements,
  commands, public APIs, or integration behavior change.

## Theme and widget boundaries

The intended visual direction is a distinct Ardoise theme shared across platforms.
Use the documented dark theme. Prefer shared Qt style facilities for
standard controls. Apply the theme explicitly from the consuming application;
never install it through static initialization.

MainWindow and Dialog use native OS title bars and buttons. Do not set FramelessWindowHint or add custom resize/drag handlers. Keep application menus in consumer content; use setWindowTitle/setWindowIcon for native decorations.

Preserve desktop behavior: keyboard navigation, visible focus, accessibility,
platform shortcuts, system dialogs, and high-DPI rendering. Validate visual work
on each available platform and identify platforms that were not checked.

Custom widgets should reuse Qt behavior and expose small, application-independent
APIs. Application-specific generation, models, service connections, storage,
settings persistence, and file workflows belong to consuming applications.
Do not create a miscellaneous utilities subsystem without a concrete request.

## Build and integration

Requirements: CMake 3.21+, Ninja for the documented workflow, a C++20 compiler,
and Qt 6.2+ Widgets, SVG and LinguistTools development files. Standalone tests require Qt Test.

```sh
cmake -S . -B build -G Ninja
cmake --build build
ctest --test-dir build --output-on-failure
```

Use `add_subdirectory()` for a source checkout or `find_package(Ardoise 0.1 CONFIG
REQUIRED)` for an installed package. Both expose `Ardoise::Widgets`. Public Qt and
C++20 requirements are propagated by that target.

Standalone builds enable examples, tests, and installation by default.
Embedded builds disable examples and installation by default and never register
their own tests. See CONTRIBUTING for options and platform setup.

Build outputs and installation staging directories belong under ignored build
directories. Never commit generated headers, libraries, CMake caches, or binaries.
The static framework library does not bundle Qt or deploy an application.

## Git workflow

- Use Git directly for repository operations.
- Use Conventional Commits: `type(optional-scope): imperative summary`.
- Do not commit, push, or create a pull request unless requested.
- Do not edit sibling applications unless the task explicitly includes them.
- Keep the MIT license; do not change it without an explicit owner decision.

## Task workflow

1. Inspect the repository and relevant documentation.
2. Identify the smallest change that satisfies the request.
3. Implement that slice without unrelated refactoring.
4. Build and run relevant tests.
5. Synchronize affected documentation.
6. Summarize the result and any actual validation limits.
